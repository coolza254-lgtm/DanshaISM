## 1. ภาพรวม

แอพ Android (Kotlin + Jetpack Compose) บันทึกรายรับ-รายจ่าย หนี้ และแผนบิลของคนคนเดียว

- ข้อมูลอยู่ในเครื่อง (Room/SQLite) ไม่มีเซิร์ฟเวอร์ ใช้ออฟไลน์ได้
- สำรอง: Android Auto Backup + ส่งออก/นำเข้าไฟล์ JSON รูปแบบ `dansha-data/1`
- อัปเดตแอพ: อ่าน GitHub Releases ล่าสุดของเรโพ → โหลด APK → เปิดตัวติดตั้งของ Android
- แจ้งเตือนในเครื่องด้วย WorkManager (ทุก 1 ชม.)
- เวลาเป็นเวลาไทยเสมอ (`Asia/Bangkok`) ไม่ว่าเครื่องตั้งโซนไหน
- ภาษาในแอพ: ไทย

### โครงสร้างเรโพ

| ที่ | หน้าที่ |
|---|---|
| `core/` | Kotlin ล้วน: โมเดลข้อมูล, อ่าน/เขียนไฟล์ข้อมูล, วันที่/รอบเงินเดือน |
| `core/.../engine/` | ตัวคำนวณทั้งหมด + `Store` (การแก้ไขข้อมูลทุกอย่าง) |
| `app/` | Room, ViewModel, หน้าจอ Compose, แจ้งเตือน, ทางลัด, ตัวอัปเดต |
| `reference/` | ระบบเดิม (JavaScript/Apps Script) ใช้เป็นสเปกที่รันได้ + `sample-data.json` (ข้อมูลสมมติ) |
| `.github/workflows/build.yml` | ทดสอบ core → build APK → สร้าง Release ที่เซ็นแล้ว (เมื่อกด Run workflow หรือ commit บน branch หลักมี `[release]`) |

### หลักการเดิมของระบบ

1. ตัวคำนวณต้องให้ผลเท่าระบบเดิม (JS) ทุกตัวเลข — `ReferenceTest` รันทั้งสองฝั่งด้วยข้อมูล/เวลาเดียวกัน ~100 วัน และขั้นตอนแก้ข้อมูล 100+ ขั้น
2. ทุกการแก้ไขผ่าน `Repository.edit { Store… }` — ทำบนสำเนา ถ้าโยน `EngineException` กลางทางจะไม่มีอะไรเปลี่ยน แล้วเขียนทั้งก้อนลง DB ใน transaction เดียว
3. ข้อมูลทั้งหมดโหลดขึ้นหน่วยความจำ; ตัวคำนวณรับ "ข้อมูลทั้งก้อน" แล้วคืนผล ไม่แก้ข้อมูล (pure)

## 3. กฎกลาง

### 3.1 วันที่/เวลา
- วันที่ = สตริง `yyyy-MM-dd`; เวลา = `yyyy-MM-ddTHH:mm:ss` เวลาไทย; ข้อความวันที่ที่ยาวกว่า 10 ตัวถูกตัดเหลือ 10
- ไฟล์ส่งออกใส่ `exported_at` ต่อท้าย `+07:00`

### 3.2 รอบเงินเดือน
- `payCycleOf(date, startDay)`: ถ้า `วันที่ของเดือน < startDay` ให้นับเป็นรอบของเดือนก่อน
- ชื่อรอบ: `"yyyy-MM Mon-Mon"` เช่น `"2026-09 Sep-Oct"` (เดือนเริ่ม–เดือนถัดไป, ใช้ชื่อเดือนอังกฤษ 3 ตัว)
- ช่วงวันของรอบ: `start = วันที่ startDay ของเดือนในชื่อรอบ`, `end = วันที่ (startDay−1) ของเดือนถัดไป` (คำนวณแบบ `first.plusDays(startDay-1)` / `first.plusMonths(1).plusDays(startDay-2)`)
- `shiftCycle(cycle, delta)` เลื่อนรอบทีละเดือน
- `Transaction.pay_cycle` ถูกคำนวณและเก็บตอนบันทึกทุกครั้ง (ไม่คำนวณใหม่ถ้าเปลี่ยน `pay_cycle_start_day`)

### 3.3 เงินและตัวเลข
- ข้อมูลเก็บเป็น `BigDecimal` (อ่าน/เขียน JSON เป็นตัวเลขตรงตัว ไม่มีศูนย์ท้าย)
- ตัวคำนวณทั้งหมดใช้ `Double` และปัดด้วย `round2` (ตามระบบเดิม) — ลำดับการปัดเศษมีผลต่อผล ห้ามสลับ
- ยอดรวมข้ามสกุล: แปลงเป็นบาทด้วยเรท

### 3.4 สกุลเงิน/เรท
- สกุลที่รองรับ: `THB, USD, JPY, CNY`
- เรทที่ใช้ = `manual_rate` (ถ้า > 0) → ไม่งั้น `auto_rate` (ถ้า > 0) → ไม่งั้น `rate_to_thb`; `THB = 1`
- ดึงเรทอัตโนมัติวันละครั้ง: `open.er-api.com` สำรอง `frankfurter.app`; กรอกเองทับได้ (null = กลับไปใช้อัตโนมัติ)
- บันทึก `rate_to_thb` = เรทที่ใช้จริง, `updated_note = "auto yyyy-MM-dd"`

### 3.5 ยอดคงเหลือบัญชี (`Balances.withBalances`)
- `flow[acc]`: income `+amount` ที่บัญชีนั้น; expense `−amount`; transfer `−amount` ที่ต้นทาง และ `+amount` ที่ปลายทาง (ไม่คิดสกุลเงิน — ดูหัวข้อ 15)
- cash/bank: `balance = opening_balance + flow`
- revolving_credit ไม่มีตัวคำนวณ: `used = opening_balance − flow`, `available = credit_limit − used`
- revolving_credit ที่มีตัวคำนวณ (ascend/spaylater): `used = outstanding` จากตัวคำนวณหนี้, `available = credit_limit − used`
- เงินที่มีตอนนี้ (บาท) = ผลรวมบัญชีที่ **active** และไม่ใช่ revolving_credit × เรท
- หนี้รวม (บาท) = ผลรวม `used` ของบัญชี revolving_credit ที่ active × เรท

## 4. โมเดลข้อมูล (ไฟล์ `dansha-data/1`)

โครงไฟล์:
```json
{ "format": "dansha-data/1", "exported_at": "...", "source": "...",
  "config": { "key": "value", ... },
  "tables": { "accounts": [...], "transactions": [...], "bills": [...], "billTemplates": [...],
              "debts": [...], "shopee": [...], "port": [...], "categories": [...], "fx": [...], "prices": [...] } }
```
- อ่านได้ทั้งแบบ `tables:{}` และแบบเก่า (ตารางอยู่ระดับบน); `format` ต้องเป็น `dansha-data/1` ถ้าระบุ
- ตอนอ่าน: แถวที่ไม่มีคีย์ (`id`, `fx.currency`, `prices.symbol`) ถูกทิ้ง; ตัวเลขว่าง=null (ตัด `,` ก่อนอ่าน); ข้อความว่าง=`""`; boolean ว่าง=false; วันที่ตัดเหลือ `yyyy-MM-dd` (ถ้าไม่ตรงรูปแบบ → error ระบุตาราง/แถว); ข้อความต้องเป็นข้อความเสมอ (`"7/11"` ห้ามกลายเป็นวันที่)
- id รูปแบบ `prefix_ + 12 hex` เช่น `txn_51d64cd50a4f` (prefix: acc, cat, txn, bill, btpl, debt, shp, port)

### 4.1 accounts
| ฟิลด์ | หมายเหตุ |
|---|---|
| id, name | name ห้ามว่าง |
| type | `cash \| bank \| revolving_credit` |
| currency | ว่าง = THB |
| opening_balance | ว่าง = 0 |
| credit_limit | ใช้กับ revolving_credit |
| color, icon, sort, active, note, created_at | |
| debt_engine | `ascend \| spaylater \| ""` (เฉพาะ revolving_credit) |
| debt_since | วันที่เริ่มนับรายการเข้าตัวคำนวณ (รายการก่อนวันนี้ไม่นับ ใช้ snapshot ของหนี้ย่อยแทน) |
| tenor_min, tenor_max | ช่วงงวดผ่อนที่บัญชีนี้รับ (ว่าง/0 = 2–24) |
| annual_rate | ดอกเบี้ยต่อปี % (ว่าง/0 = 25) |

กฎ: ลบบัญชีที่มีรายการแล้วไม่ได้ (ต้องปิดใช้งาน)

### 4.2 transactions
| ฟิลด์ | หมายเหตุ |
|---|---|
| id, date, pay_cycle | pay_cycle คำนวณตอนบันทึก |
| type | `income \| expense \| transfer` |
| account_id | ต้องมี; transfer = ต้นทาง |
| to_account_id | transfer เท่านั้น ต้องไม่ซ้ำต้นทาง |
| amount | ต้อง > 0 |
| currency, category_id, subcategory_id, note | |
| source | `manual \| bill_plan \| shopee \| debt \| travel \| mytax \| nodiscount \| adjust` (ว่าง = manual) |
| ref_id | `bill_plan` → id ของบิล |
| created_at | |
| full_price, gov_subsidy | 60/40 |
| discount | No Discount: ราคาก่อนลด − ที่จ่ายจริง |
| claim | `"" \| open \| sub:yyyy-MM-dd \| paid:yyyy-MM-dd` |

### 4.3 bills (แผนบิลของแต่ละรอบ)
`id, pay_cycle, group (income|A|B), name, category_id, account_id, est_amount, actual_amount, status (planned|paid), due_date, paid_date, txn_id, template_id, note, to_account_id, sort, section`
- `group` ใช้คำนวณยอดคงเหลือ: income = รายรับ, A = รายจ่ายประจำ/หนี้/ครั้งเดียว, B = เดินทาง/วางแผนใช้
- `section` ใช้จัดหมวดการแสดง: `salary | income | claim | fixed | debt | once | travel | planned` — เมื่อมี section ระบบกำหนด group ให้อัตโนมัติ (`groupOf`)
- `to_account_id` ไม่ว่าง = บิลนี้คือ "โอนไปชำระบัญชีนั้น" (เช่น จ่ายหนี้)
- `template_id` พิเศษ: `auto:debt`, `auto:travel`, `claim:<วันที่ส่งเบิก>`

### 4.4 billTemplates
`id, group, name, category_id, account_id, est_amount, due_day, active, sort, note, to_account_id, section` — ตัวต้นแบบรายเดือน

### 4.5 debts (หนี้ย่อยของบัญชี Ascend)
`id, account_id, txn_date, kind (cash|installment|convert|fullpay_snapshot), description, principal, tenor, annual_rate, installment, first_due_date, status, note, created_at, snap_date, snap_remaining, snap_paid_periods, snap_last_interest_date, txn_id`
- `cash` = กดเงินสด, `installment` = ผ่อนตอนซื้อ, `convert` = แปลงยอดเต็มจำนวนเป็นผ่อน, `fullpay_snapshot` = ยอดเต็มจำนวนยกมา
- snapshot (`snap_*`) = จุดตั้งต้นที่คัดจากแอพ Ascend จริง (คงเหลือ, งวดที่จ่ายแล้ว, วันคิดดอกล่าสุด)
- `status = deleted` ถูกข้าม
- กฎตอนบันทึก: `principal > 0`; ถ้าไม่ใช่ fullpay_snapshot ต้องมี tenor ≥ 1 และ (ถ้าไม่มี snapshot) อยู่ในช่วง tenor_min–tenor_max ของบัญชี

### 4.6 shopee (ออเดอร์ Shopee)
`id, order_date, item, shop, price, tenor, annual_rate, account_id, status (ordered|active|cancelled|waiting), note, created_at, pay_method (spaylater|full), installment, category_id, txn_id, order_no, received_date, kind ("" | food)`
- `pay_method = full` → สร้างรายจ่าย `"Shopee: <item>"` (source `shopee`) ผูก `txn_id`
- `kind = food` → ค่าอาหารที่จ่ายด้วย SPayLater (ดูหัวข้อ 7.4)

### 4.7 port (ธุรกรรมพอร์ตลงทุน)
`id, date, symbol, name, asset_type (stock|etf|fund|gold|other), side (buy|sell|dividend|fee), qty, price, currency, fx_rate, fee, tax, broker (ตั้งต้น "Dime!"), note, created_at`

### 4.8 categories
`id, name, type (income|expense), parent_id, color, icon, sort, active` — 2 ระดับ (หมวดหลัก/ย่อย); ลบหมวดหลักจะลบหมวดย่อย; ถ้าถูกใช้ในรายการแล้วลบไม่ได้ (ต้องปิดใช้งาน)

### 4.9 fx / prices
- `fx(currency, auto_rate, manual_rate, rate_to_thb, updated_note)`
- `prices(symbol, price, currency, updated_at)` — ผู้ใช้กรอกราคาเอง ไม่ดึงราคาสด

### 4.10 หมวดตั้งต้น (seed)
รายรับ: เงินเดือน · รายได้เสริม(ฟรีแลนซ์, ขายของ) · ดอกเบี้ย/ปันผล · รายรับอื่นๆ
รายจ่าย: อาหาร(อาหารหลัก, ขนม/เครื่องดื่ม, ร้านสะดวกซื้อ, เดลิเวอรี่) · เดินทาง(รถสาธารณะ, แท็กซี่/Grab, น้ำมัน) · ที่พัก/บ้าน(ค่าเช่า, ค่าไฟ, ค่าน้ำ, อินเทอร์เน็ต) · โทรศัพท์/สมาชิก(ค่าโทรศัพท์, Subscription) · ช้อปปิ้ง(Shopee, เสื้อผ้า, ของใช้) · สุขภาพ(ยา, โรงพยาบาล) · บันเทิง(เกม, หนัง/เพลง, เที่ยว) · ครอบครัว/แฟน · ชำระหนี้(ดอกเบี้ย, ค่าธรรมเนียม) · ลงทุน · อื่นๆ
(ทุกหมวดมีสีพาสเทลและไอคอน emoji — ดูใน `Schema.kt`)

## 5. การแก้ไขข้อมูล (`Store`) — กฎธุรกิจ

ทุกเมธอดทำบนสำเนา; error → ไม่มีอะไรเปลี่ยน

### 5.1 รายการ (transaction)
- ตรวจ: มีวันที่ (รูปแบบถูก), type ถูก, มี account_id, `amount > 0`, transfer ต้องมีปลายทางและไม่ซ้ำต้นทาง
- คำนวณ `pay_cycle`; `source` ว่าง = `manual`
- **ร่วมจ่าย 60/40** (copay=true): ต้องเป็นรายจ่าย; ถ้ากำหนด `copay_account_id` ต้องจ่ายจากบัญชีนั้น; ต้องกรอก `full_price`; แล้ว `amount = full_price − gov` (ดูหัวข้อ 8); แก้ไขโดยส่ง copay=false = ยกเลิกสิทธิ (ล้าง gov_subsidy/full_price)
- หลังบันทึกทุกครั้งเรียก `syncFoodOrder` (หัวข้อ 7.4)
- **ลบรายการ**: ลบหนี้ย่อยที่ผูก `txn_id`; ลบออเดอร์ food ที่ผูก; ปลดลิงก์ `txn_id` ในออเดอร์ Shopee อื่น; ถ้า `source=bill_plan` ให้บิลต้นทางกลับเป็น planned (ล้าง actual_amount/paid_date/txn_id)

### 5.2 แผนบิล/แม่แบบ
- ตรวจ: group ∈ {income,A,B}, ชื่อไม่ว่าง, `est_amount ≥ 0`; ถ้ามี section → group = `groupOf(section)`; group income → `to_account_id` ล้างทิ้ง
- แก้ยอดจริงของบิลที่จ่ายแล้ว → แก้ `amount` ของรายการที่ผูกด้วย
- ลบบิลที่จ่ายแล้วไม่ได้ (ต้องกด "ยกเลิกการจ่าย")
- **สร้างแผนรอบจากแม่แบบ** (`generateCycle`): ทุกแม่แบบที่ active และยังไม่มีในรอบ (เทียบ `template_id`) เรียงตาม sort; ถ้าแม่แบบมี `to_account_id` ของบัญชีที่มีตัวคำนวณหนี้ → ใช้ยอด+วันครบกำหนดจากตัวคำนวณแทน; `due_date = dueDateInCycle(cycle, due_day)`
- `dueDateInCycle`: `due_day ≥ startDay` → อยู่เดือนแรกของรอบ ไม่งั้นเดือนถัดไป; ตัดที่วันสุดท้ายของเดือน
- **กดจ่าย/รับ** (`payBill`): ต้อง planned, ยอด > 0, มีบัญชี; สร้างรายการ type = income (group income) / transfer (มี to_account) / expense; `source=bill_plan`, `ref_id=bill.id`; บิล → paid + actual_amount/paid_date/txn_id
- **ยกเลิกการจ่าย**: ลบรายการ แล้วบิลกลับ planned
- **รับเงินเดือนจากสลิป** (`receiveSalary`): หาบิลเงินเดือนของรอบที่ยังไม่จ่าย (section salary หรือชื่อมี "เงินเดือน") ไม่มีก็สร้าง แล้ว payBill
- **เพิ่มหลายรายการ** (`addBulk`, หัวข้อ 9.4)

### 5.3 หนี้
- `cashDraw`: เบิกเงินสดจากบัญชี Ascend → สร้างหนี้ย่อย (kind cash) + (ถ้าระบุบัญชีปลายทาง) รายการโอน `source=debt` ผูก `txn_id`
- ลบหนี้ย่อยได้โดยตรง

### 5.4 Shopee
- `recordPurchase`: จ่ายเต็ม → สร้างรายจ่ายอัตโนมัติ; SPayLater → ถ้าผ่อน >1 งวดต้องกรอกค่างวดจากแอพ Shopee; `receivedDate`: null=นับจากวันสั่ง (แบบเดิม), ""=ยังไม่กดรับ (`status=waiting`), วันที่=วันกดรับ
- `updateShopee`: วันรับต้องไม่ก่อนวันสั่ง; ยกเลิกออเดอร์จ่ายเต็ม → ลบรายจ่ายที่ผูก; แก้ราคา → แก้รายจ่าย; แล้ว `syncSplBills`
- `syncSplBills(accountId)`: อัปเดต `est_amount`/`due_date` ของบิลแผนที่ `to_account_id` = บัญชีนั้น (ยังไม่จ่าย) ให้ตรงกับบิลที่ตัวคำนวณได้ในแต่ละรอบ

### 5.5 พอร์ต
- ตรวจ: side ∈ buy/sell/dividend/fee, symbol ไม่ว่าง (บังคับตัวพิมพ์ใหญ่), มีวันที่, สกุลรองรับ, buy/sell ต้อง qty > 0, price ≥ 0; THB → fx_rate = 1; ต่างสกุลต้องกรอก fx_rate จริง; asset_type ตั้งต้น stock; broker ตั้งต้น "Dime!"

## 6. ตัวจำลองหนี้ Ascend PayNext / PayNext Extra (`DebtEngine`)

ตรวจกับ statement จริง 23 ฉบับ — **ห้ามเปลี่ยนลำดับการคำนวณ/การปัดเศษ** ควรเก็บเป็นชุดทดสอบทอง (golden tests)

### 6.1 ปฏิทิน
- ตัดรอบบิลวันที่ **15**, ครบกำหนด **วันที่ 1 ของเดือนถัดไป**; รอบการใช้ 16–15
- วันออกบิลถัดไป ≥ d: วันที่ 15 ของเดือนนั้น ถ้าผ่านแล้วใช้วันที่ 15 เดือนถัดไป
- ลำดับเหตุการณ์ในวันเดียวกัน: **กู้/ซื้อ (1) → ชำระ (2) → ออกบิล (3) → ครบกำหนด (4)**

### 6.2 ค่างวด/ดอกเบี้ย
- ค่างวด = `P·r / (1 − (1+r)^−n)`, `r = annual_rate / 12`, ปัด 2 ตำแหน่ง (ใช้ค่า `installment` ที่กรอกถ้ามี)
- ดอกเบี้ยนับวันจริง: `เงินต้นคงเหลือ × annual_rate × จำนวนวัน / 365` นับจากวันคิดดอกล่าสุด (สะสมเป็น `A`)
- อัตราต่อปี: ของหนี้ย่อย (`annual_rate`≠0) ไม่งั้นของบัญชี (ตั้งต้น 25%)
- ตอนออกบิล ก้อนหนี้: `interestDue = ปัด(A + R·rate·(วันครบกำหนด − วันคิดดอกล่าสุด)/365)`; `k += 1`; `principalDue = ค่างวด − interestDue − Ip`; งวดสุดท้าย (k ≥ tenor) หรือ principalDue ≥ เงินต้นคงเหลือ → ตัดเท่าเงินต้นคงเหลือ; ไม่ต่ำกว่า 0
- `Ip` = ดอกที่จ่ายล่วงหน้าหลังครบกำหนดโดยไม่มีบิลค้าง → ไปลดเงินต้นบิลถัดไป
- ก้อนที่ `l.start > วันออกบิล` ยังไม่ออกบิล; ก้อนที่มีบิลเดือนเดียวกันอยู่แล้วไม่ออกซ้ำ

### 6.3 โหมดปัดดอกเบี้ย (`interestMode`)
0 = ปัดครึ่งขึ้นต่อก้อน (ระบบเดิม ใช้ในเทสต์เทียบ JS), 1 = ปัดทิ้ง, 2 = แบบ 1 + ยอดสะสมรวมปัดทิ้ง, **3 = ปัดครึ่งขึ้นรายก้อนแล้วค่อยรวม (ค่าที่แอพใช้ ตรงกับแอพ Ascend: ยอดปิดหนี้ = Σ เงินต้น + Σ ดอกแต่ละก้อนที่ปัดเป็นสตางค์แล้ว)**

### 6.4 การตัดชำระ (ลำดับ)
1. ค่าธรรมเนียมค้าง
2. รายการที่ออกบิลแล้ว (ก้อนผ่อน + ยอดเต็มจำนวนที่ออกบิล) เรียงตามวันที่เริ่ม เก่าก่อน — แต่ละก้อน **ดอกก่อนต้น** ไม่เกินยอดบิลของก้อนนั้น
3. ยอดเต็มจำนวนที่ยังไม่ออกบิล (เรียงตามลำดับ)
4. ส่วนเกิน → ก้อนผ่อนเก่าสุดก่อน (ดอกของก้อน → ต้นของก้อน) ติดธง `extra`
- ก่อนตัดชำระทุกครั้ง คิดดอกสะสมถึงวันนั้นทุกก้อน
- บันทึก log `payment` พร้อม parts และ `unapplied`

### 6.5 ยอดเต็มจำนวน (full-pay) และการแปลงอัตโนมัติ
- รายจ่ายจากบัญชี Ascend (หลัง `debt_since`) = ยอดเต็มจำนวน (purchase) ออกบิลในรอบถัดไป
- สิ้นวันครบกำหนด: ถ้ายอดเต็มจำนวนที่ออกบิลของวันนั้นยังค้าง **≥ 300** → แปลงเป็นหนี้ผ่อน **5 งวด** อัตโนมัติ (`id = auto_<วันที่>`, kind `auto`)
- ถ้ายังมีบิลผ่อนค้างหรือยอดเต็ม <300 ค้าง → นับ "ผิดนัด": ถ้าเงินต้นรวมของก้อนผ่อน ≥ 1000 → ค่าธรรมเนียม **50** (ครั้งแรก) / **100** (ครั้งที่สองติดกันขึ้นไป); จ่ายครบ → รีเซ็ตตัวนับ
- ก้อน `convert` ที่ไม่มี snapshot = แปลงยอดเต็มจำนวนในบิลปัจจุบัน (ตัดยอดเต็มจำนวนที่ออกบิลเดือนนั้น เก่าก่อน และคิดดอกตั้งแต่ 16 ของรอบนั้น)

### 6.6 ข้อมูลเข้า (`DebtTracker.debtInput`)
- loans = หนี้ย่อยที่ไม่ใช่ `fullpay_snapshot` และ status ≠ deleted
- purchases = หนี้ย่อย `fullpay_snapshot` + รายจ่ายของบัญชีนี้ที่ `date ≥ debt_since`
- payments = **โอนเข้า** บัญชีนี้ หรือ **รายรับ** ของบัญชีนี้ ที่ `date ≥ debt_since`
- snapshot: เริ่มก้อนที่วัน `snap_date` ด้วยเงินต้น `snap_remaining`, งวดที่จ่ายแล้ว `snap_paid_periods`, คิดดอกต่อจาก `snap_last_interest_date`

### 6.7 ผลลัพธ์ที่หน้าจอใช้ (`AscendState`)
`outstanding` (เงินต้นรวม), `accruedInterest`, `fees`, `payoffToday = outstanding + accruedInterest + fees`, `currentBill` (บิลที่ต้องจ่ายตอนนี้: ยอดบิลก้อนผ่อนที่เปิด + ยอดเต็มที่ออกบิลและยังไม่ถึงกำหนด + ค่าธรรมเนียม), `nextBill` (จำลองถึงวันออกบิลถัดไปโดยสมมติจ่ายเต็มบิลตรงกำหนด), `lastStatement`, `loans`, `pendingFull`, `payments` (20 รายการล่าสุด), `events`, `dailyInterest`, `cycleSpend` (ยอดใช้ในรอบบิล 16–15 = ซื้อเต็มจำนวน + กดเงินสด + ผ่อนตอนซื้อ), `schedule` (ตารางผ่อน ~2 ปี สมมติจ่ายตรงบิลทุกงวด) และ `bills` (26 บิลข้างหน้า)

### 6.8 ฟีเจอร์เกี่ยวข้อง
- `quote(date, amount?)`: ยอดปิดหนี้ ณ วันที่ + ถ้าระบุยอด จะแสดงการตัดชำระ/ยอดคงเหลือหลังจ่าย
- เทียบยอดกับแอพ Ascend: ผู้ใช้กรอกยอดจริง → บอกส่วนต่าง → ไล่รายการซื้อเต็มรอบนี้ (ขึ้น "อาจซ้ำ" ลบได้) → ปุ่มเดียวเพิ่มยอดที่ขาด; กันจดรายการซ้ำภายใน 10 นาที (`DebtReconcile.kt`)

## 7. SPayLater / Shopee

### 7.1 การคิดงวด (`SPayLater`)
- ใช้ **ค่างวดที่ผู้ใช้กรอกจากแอพ Shopee** (ไม่คำนวณดอกเอง); 1 งวด = ราคาเต็ม; ไม่ได้กรอกค่างวด = `ราคา/งวด` และงวดสุดท้ายปรับเศษให้ผลรวมเท่าราคา
- วันที่ใช้นับรอบบิล (`basisDate`): food → วันสั่ง; มี `received_date` → วันนั้น; `status=waiting` → วันสั่ง + `shopee_receive_days`; อื่นๆ → วันสั่ง
- **ตัดรอบวันที่ 15**: วันที่ < 15 นับเป็นรอบบิลเดือนก่อน; งวดที่ k ครบกำหนด **วันที่ 25 ของเดือน (เดือนรอบบิล + k)**
- วันออกบิล (`stmtDate`) = วันที่ 15 ของเดือนเดียวกับวันครบกำหนด

### 7.2 การตัดชำระ
- ชำระ = **โอนเข้า** หรือ **รายรับ** ของบัญชี SPayLater (หลัง `debt_since`) รวมเป็นก้อน แล้วตัดงวดที่ครบกำหนดก่อนสุดก่อน (เรียง due แล้ว order id); เกินยอด → เป็น `credit`
- `outstanding` = ผลรวมค่างวดที่เหลือทั้งหมด (ออเดอร์ที่ไม่ใช่ cancelled)
- `currentBill`: มีงวดเลยกำหนด → ผลรวมทุกงวดที่เลย (overdue=true); ไม่งั้นงวดถัดไปถ้าอยู่เดือนเดียวกับวันนี้
- `nextBill`/`bills`: งวดครบกำหนดตั้งแต่วันนี้เป็นต้นไป (รวมยอดตามวันครบกำหนด)
- `perOrder`: งวดที่จ่ายแล้ว/ยอดค้าง/งวดถัดไปของแต่ละออเดอร์
- `impliedRate`: หาอัตราดอกต่อปีจากค่างวด (bisection 60 รอบ) ใช้โชว์ "ดอกจริง"

### 7.3 สถิติ Shopee
จำนวน/ยอดรวม/เฉลี่ย/สัดส่วนผ่อน/ดอกรวม (`ค่างวด × งวด − ราคา`), แยกรายเดือน (เต็ม vs ผ่อน), ร้านยอดสูงสุด 8 อันดับ — ไม่นับ cancelled และ food

### 7.4 ค่าอาหารจ่ายด้วย SPayLater (`syncFoodOrder`)
รายจ่าย (ไม่ใช่ `source=shopee`) บนบัญชี SPayLater → สร้าง/อัปเดตออเดอร์ `kind=food` 1 งวด (`price = amount`, `received_date = วันที่จ่าย`, ไม่ต้องกดรับ) แล้ว `syncSplBills`; ย้ายบัญชี/เปลี่ยนเป็นรายรับ/ลบรายการ → ลบออเดอร์ที่ผูก

## 8. โครงการร่วมจ่าย 60/40 (`Copay`)

- เปิดด้วย `copay_enabled = true`; สิทธิใช้ได้เมื่อ `copay_start ≤ วันที่ ≤ copay_end`
- ผู้ใช้กรอก **ราคาเต็ม** → `gov = max(0, ปัด2(min(ราคา × rate, เหลือวันนี้, เหลือเดือนนี้, เหลือทั้งโครงการ)))`, `amount (จ่ายเอง) = ราคา − gov`
- นอกช่วงโครงการ: `gov = 0`, `self = ราคา`, เหตุผล "นอกช่วงโครงการ"
- การใช้สิทธิ = รายการที่ `gov_subsidy > 0` และอยู่ในช่วงโครงการ; รายวัน = วันที่เดียวกัน; รายเดือน = `date.take(7)` เดียวกัน (ไม่สะสมข้ามเดือน); รวมทั้งโครงการ; ตอนแก้รายการ ไม่นับตัวเอง
- บัตรหน้าแรก: เหลือกี่วัน, รัฐช่วยได้วันนี้อีก = `min(dayLeft, monthLeft, totalLeft)`, "ควรซื้อราคาเต็มเท่าไหร่ถึงใช้สิทธิวันนี้ครบ" = `leftToday / rate`
- ค่าตั้งต้นฝังตามโครงการ เฟส 2 (1 ต.ค. – 30 พ.ย. 2026, 60%, 200/วัน, 1,000/เดือน, 1,000 ทั้งโครงการ, เวลา 06:00–23:00 — `copay_hours` เก็บไว้แต่ไม่พบการตรวจในโค้ดที่อ่าน)

## 9. แผนบิลแบบแบ่งหมวด, ค่าเดินทาง, Staff Claim

### 9.1 ยอดคงเหลือคาดการณ์ (`Plan.summary`)
ต่อรอบ: ผลรวม est_amount ของบิล `planned` ตาม group และ actual_amount ของ `paid`
`projected = cashNow + incomePending − aPending − bPending` (ทุกตัวปัด 2)

### 9.2 หมวดในหน้าแผนบิล
ลำดับแสดง: รายรับ(salary/income/claim) → รายจ่ายประจำ(fixed) → หนี้สิน(debt) → ครั้งเดียว(once) → ค่าเดินทาง(travel) → วางแผนใช้(planned)
`groupOf`: income/salary/claim → `income`; travel/planned → `B`; ที่เหลือ → `A`
แถวเก่าไม่มี section → เดาจาก group/`to_account_id`/`template_id` (`displaySection`)

### 9.3 `syncPlan(cycle)` — แถวที่แอพจัดการเอง
- **หนี้สิน**: ทุกบัญชี active ที่มีตัวคำนวณ (ascend/spaylater) → ถ้าไม่มีแถวในรอบและมียอดบิลในรอบ → สร้าง (`template_id=auto:debt`, จ่ายจากบัญชี bank แรกที่ active ไม่งั้น cash); ถ้ามีแล้วและยังไม่จ่าย → อัปเดตยอด/วันครบกำหนดให้ตรงตัวคำนวณ (ไม่มียอด → 0)
- **ค่าเดินทาง**: ยอด `remaining` ของ `PlanBook.travel` (`template_id=auto:travel`, group B) พร้อมโน้ต "ทำงาน N วัน (กะดึก M) · เหลือ K วัน"

### 9.4 เพิ่มหลายรายการจากข้อความ
บรรทัดละ `หมวด | ชื่อ | ยอด | วันที่(ไม่บังคับ) | โน้ต(ไม่บังคับ)`; บรรทัดขึ้นต้น `#` ข้าม
คำหมวด: เงินเดือน/salary, รายรับ/income, ประจำ/รายจ่ายประจำ/fixed/บิล, หนี้/หนี้สิน/debt, ครั้งเดียว/once, เดินทาง/ค่าเดินทาง/travel, วางแผน/วางแผนใช้/planned
ตรวจ: ≥3 ช่อง, รู้จักหมวด, มีชื่อ, ยอด ≥ 0, วันที่ 1–31
ประจำ/รายรับ/หนี้ → แม่แบบ (ชื่อซ้ำ = แก้ยอด/วัน); ครั้งเดียว/วางแผนใช้ → ใส่ในรอบที่เลือก; หมวดเดาด้วย QuickEntry

### 9.5 ค่าเดินทางไปทำงาน
- วันทำงานของรอบเก็บใน config `work:<yyyy-MM>`; กะดึก (`*`) = เลิก 23:00 ขากลับ Grab
- ค่าที่เผื่อ: ขาไป = `travel_bus` (20), ขากลับวันปกติ = `travel_bus`, ขากลับกะดึก = `travel_grab` (150); ขาที่ยกเว้น = 0
- ยกเว้นขาไป/ขากลับพร้อมเหตุผล (มีคนไปส่ง, บริษัทจ่าย…) → ไม่ต้องเผื่อเงินและไม่นับว่าค้างจด
- ต่อวัน: `done` = (ขาไปจดแล้ว หรือยกเว้น) และ (ขากลับจดแล้ว หรือยกเว้น); `pending` = ผลรวมขาที่ยังไม่จด; `saved` = เผื่อ − จ่ายจริงของขาที่จดแล้ว
- สรุปรอบ: จำนวนวัน/กะดึก, เหลือกี่วัน, เผื่อทั้งรอบ, ยังต้องเตรียม, จ่ายจริง (รายจ่ายค่าเดินทางทั้งหมดในรอบ), ประหยัดได้
- จดค่ารถ: `logTravel` (source `travel`, โน้ต "ค่ารถไปทำงาน"/"ค่ารถกลับบ้าน", หมวด "รถสาธารณะ" ไม่เจอใช้ "เดินทาง", บัญชีเงินสด); จดซ้ำ = แก้ยอดเดิม; ลบ = ใส่ amount null
- ระบบหา "ขาไป/ขากลับ" ของวันจาก **ข้อความโน้ต** หรือ `claim` ไม่ว่าง (จุดอ่อน — หัวข้อ 15)

### 9.6 Staff Claim
- `logGrab`: รายจ่าย `source=travel`, `claim=open`, หมวด "แท็กซี่/Grab", จ่ายจากบัญชีจ่าย Grab (เดา "true"/TrueMoney)
- `setClaimable`: สลับเบิกได้/ไม่ได้ (ส่งเบิกแล้วแก้ไม่ได้)

## 10. ออมแบบบังคับตัวเอง (`SelfSave`) — เปิด/ปิดแยกกัน

### Myself Tax
- ทุก **รายจ่าย** ตั้งแต่ `mytax_start`: `ภาษี = amount × pct / 100` โดย pct = `mytax_rate:<subId>` ?? `mytax_rate:<catId>` ?? `mytax_default_pct` (ตั้งต้น 0)
- ทุก **รายรับ** (ยกเว้นรายรับที่มาจากบิล claim): `amount × mytax_income_pct / 100` (ตั้งต้น 1%)
- เปิดครั้งแรก → `mytax_start = วันนี้`

### No Discount
- รายจ่ายที่มี `discount > 0` ตั้งแต่ `nodiscount_start` → ยอดเก็บ = `discount` (ฟอร์มจดรายการมีช่องราคาก่อนลด)

### ยอดค้างโอน
`ค้าง = ยอดสะสม − ผลรวมรายการโอน source = mytax/nodiscount ตั้งแต่วันเริ่ม` (ไม่ติดลบ)
`paySelfSave`: โอนจากบัญชีหนึ่งเข้า `savings_account_id` เป็นรายการ transfer แยกยอดภาษี/ส่วนลด (โน้ต "Myself Tax"/"No Discount"); ต้นทาง ≠ ปลายทาง
หน้า "กระปุก" แสดงยอดค้าง ยอดวันนี้ และรายการที่ทำให้เกิดยอด

## 11. ภาพรวมรายรอบ, เช็คก่อนซื้อ, หน้าแรก

### 11.1 Outlook (`Outlook.cycles`) — รอบนี้ + (n−1) รอบถัดไป (แอพใช้ 6; เช็คก่อนซื้อใช้ 7)
- รอบที่มีแถวบิล → ใช้บิลจริง (paid นับ 0 ในส่วนที่ยังไม่จ่าย); ไม่มี → ใช้แม่แบบที่ active
- `income` (ยังไม่เข้า), `incomeFull` (ทั้งรอบ ใช้คิดภาระหนี้), `planned` = รายจ่ายตามแผนที่ **ไม่ใช่** การโอนไปบัญชีที่มีตัวคำนวณหนี้
- `debtDue` = ยอดบิลหนี้จากตัวคำนวณที่ครบกำหนดในรอบ และ ≥ วันนี้ (ไม่นับซ้ำวันเดียวกัน)
- `remaining = (รอบนี้: cashNow + income, รอบถัดไป: income) − planned − debtDue`

### 11.2 เช็คก่อนซื้อ (`checkPurchase`)
- อินพุต: ราคา, วิธีจ่าย (spaylater|full), งวด, ค่างวด, อัตราดอก, วันที่
- ค่างวดใหม่ตกอยู่ในรอบไหน (งวด k ใช้ `SPayLater.dueDate`); จ่ายเต็ม = ทั้งก้อนในรอบของวันที่ซื้อ
- ตารางเทียบ 1/3/6/10/12 งวด ประมาณดอกด้วยอัตรา (ไม่ระบุ = 25%/ปี)
- `pctOfLeft = ราคา / เงินคงเหลือรอบนี้`; ภาระหนี้ `burden = (debtDue + ค่างวดใหม่) / incomeFull × 100`
- ธง: ราคา ≥ `shop_warn_pct`% ของที่เหลือ (แดงถ้า ≥50, เหลืองถ้าไม่ถึง), ไม่มีรายรับในแผน (เหลือง), รอบนี้ติดลบอยู่แล้ว (แดง), รอบไหนเหลือ < `shop_buffer` (แดง), ภาระสูงสุด ≥40% (แดง) / ≥30% (เหลือง), ผ่อนเสียดอก (เหลือง)
- verdict: มีแดง → red; มีเหลือง → yellow; ไม่งั้น green

### 11.3 ตัวเลขหน้าแรก (`Home.figures`)
- เงินที่มีตอนนี้, หนี้คงเหลือ, **สิ้นรอบเหลือ** = `plan.projected` (null ถ้ารอบนี้ไม่มีแผนบิล)
- **ใช้ได้วันละ** = `(projected หรือ cashNow ถ้าไม่มีแผน) / จำนวนวันถึงสิ้นรอบ (รวมวันนี้, อย่างน้อย 1)`
- บิลหนี้ถัดไป: ใกล้สุดจากทุกบัญชี (currentBill ก่อน nextBill; ธง overdue)
- ยอดใช้ในรอบบิล 16–15 ของ Ascend; บัตรร่วมจ่าย; พอร์ต (ถ้ามี)

## 12. จดไว (QuickEntry)

อินพุตตัวอย่าง: `กาแฟ 35`, `ข้าวมันไก่ 50 สด`, `grab 120 tm`, `+15000 เงินเดือน`, `โอน 500 ktb`

**แยกข้อความ**: ขึ้นต้น `+` = รายรับ, `-`/`−` = รายจ่าย; คำนำหน้า "รับ/ได้เงิน/เงินเข้า/income" = รายรับ, "โอน/transfer" = โอน; ตัวเลขแรกที่ตรง regex (รองรับ `1,234.50`, `฿`, `บ/บาท/b`) = ยอด; โทเคนที่ตรงชื่อเล่นบัญชี = บัญชี; ที่เหลือ = โน้ต
**ชื่อเล่นบัญชี** (ฮาร์ดโค้ด): สด/เงินสด/cash → บัญชีชนิด cash; tm/true/ทรู/truemoney; kbank/kb/กสิกร/kplus; ktb/กรุงไทย/next; bbl/bualuang/กรุงเทพ/bangkok; g/gw/เป๋า/เป๋าตัง/gwallet; spl/spaylater/paylater; pn/paynext (ไม่ใช่ Extra); ex/extra; scb/ไทยพาณิชย์ — จับคู่กับ "ชื่อ/ไอคอน" ของบัญชี

**ให้คะแนนหมวด**:
1. จากประวัติ: ความคล้ายโน้ต (ตรงเป๊ะ 1 > ขึ้นต้น 0.6–0.95 > มีคำร่วม 0.55–0.8 > มีอยู่ในกัน 0.6 > dice bigram ×0.7; ตัดทิ้งถ้า <0.45) + โบนัสยอดเท่าเป๊ะ +0.5 (±10% +0.1) × ถ่วงเวลาของวัน (±2 ชม. ×1.25) × ถ่วงความใหม่ `0.4 + 0.6·e^(−อายุวัน/60)`; รวมคะแนน แล้วปรับเป็น 0–1 ด้วย `1 − e^(−s/1.2)`
2. ชื่อหมวด/หมวดย่อยปรากฏในข้อความ (0.7–0.8) และตารางคำที่เกี่ยวข้อง (0.5–0.7) เช่น กาแฟ→ขนม/เครื่องดื่ม, grab→แท็กซี่/Grab, bts/mrt→รถสาธารณะ, netflix/claude→Subscription
3. เลือกสูงสุด 3 หมวด (ไม่ซ้ำ); บัญชี = ที่ระบุ > บัญชีที่ใช้บ่อยกับโน้ตนี้ > บัญชีเริ่มต้นของประเภท; ยอด = ที่พิมพ์ > ยอดที่จ่ายบ่อยของรายการนั้น
ไม่ส่งข้อมูลออกนอกเครื่อง

## 13. พอร์ตลงทุน, แจ้งเตือน, ส่งออก/อัปเดต

### 13.1 พอร์ต (`PortfolioCalc`)
ต้นทุนถัวเฉลี่ยแยกสกุลหลักทรัพย์และเป็นบาท; เรียงธุรกรรมตามวันที่/created_at
- buy: `qty += q; cost += q·price + fee` (บาท: × fx_rate ของรายการ)
- sell: ขายไม่เกินที่มี; `proceeds = q·price − fee − tax`; กำไรรับรู้ = `proceeds − avgCost·q` (บาท: `proceeds·rate − avgCostThb·q`)
- dividend: สุทธิ = `price − tax`; fee: นับเป็นขาดทุนรับรู้
- มูลค่า = qty × ราคาที่กรอกเอง × เรทปัจจุบัน; แยกกำไรจากราคา/จากค่าเงิน; สรุปตามประเภทสินทรัพย์; รายการไม่มีราคา = `missingPrice` (ใช้ต้นทุนแทนในมูลค่ารวม)

### 13.2 แจ้งเตือน (WorkManager ทุก 1 ชั่วโมง)
- ส่งเมื่อถึงชั่วโมงที่ตั้ง (สรุปรายวัน: `daily_summary_hour`; ถ้าปิดสรุป ใช้ 9 โมงสำหรับเตือนครบกำหนด) และยังไม่ส่งของวันนั้น
- เตือนครบกำหนด: หนี้ — เลยกำหนด (ทุกวัน) หรืออีก N วันที่อยู่ใน `debt_reminder_days`; บิลในแผนที่ยังไม่จ่าย (ไม่รวมบิลที่โอนไปบัญชีหนี้ที่มีตัวคำนวณ) — อีก N วันตาม `bill_reminder_days`
- สรุปรายวัน: เงินที่มี, หนี้รวม, คงเหลือหลังแผน, ใช้ได้วันละ, พอร์ต, รับ/จ่ายวันนี้ + 10 รายการ, ครบกำหนดใน 10 วัน, สถานะ 60/40
- ปุ่มแชร์สรุปเป็นข้อความหรือรูปการ์ด (ดูตัวอย่างก่อนส่ง)
- ขอสิทธิ์แจ้งเตือน (Android 13+) ครั้งแรก

### 13.3 ส่งออก/นำเข้า
- ส่งออกไฟล์ `dansha-data-yyyy-MM-dd.json` (หนึ่งแถวต่อหนึ่งบรรทัด อ่านง่าย/diff ได้); นำเข้าแล้วถามยืนยันก่อนแทนที่ทั้งหมด; มี "เริ่มใหม่" (seed หมวด+config+fx)

### 13.4 อัปเดตแอพ
อ่าน `releases/latest` ของเรโพใน `BuildConfig.GITHUB_REPO`; tag `v1.0.<run_number>` และเลขท้าย = `versionCode`; หาไฟล์ `.apk` แรก; โหลดลง `cache/updates`; ต้องอนุญาต "ติดตั้งแอพที่ไม่รู้จัก"; เช็คอัตโนมัติตอนเปิดแอพ
CI: secrets `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD` (alias `dansha`)

### 13.5 กลับมาจดต่อ (`CatchUp`) — เมื่อไม่ได้จดหลายวัน
- หน้าแรกขึ้นการ์ด "ไม่ได้จดมา N วัน" เมื่อวันที่จดล่าสุด (ตาม `created_at`) ห่างจากวันนี้ ≥ 2 วัน; เปิดได้จากเมนูเพิ่มเติมเสมอ
- **จดย้อนหลังหลายรายการ**: บรรทัดวันที่ (`28/10`, `28/10/69`, `28 ต.ค.`, `2026-10-28`, `วันนี้`, `เมื่อวาน`, `เมื่อวานซืน`) เปลี่ยนวันของบรรทัดถัดไป; `28/10 กาแฟ 35` = วันที่+รายการในบรรทัดเดียว; ไม่ระบุปี = ปีนี้ (ถ้าเลยวันนี้ไปเกิน 31 วัน = ปีที่แล้ว); `7/11 …` ถือเป็นชื่อร้าน; บรรทัด `#` ข้าม
- แต่ละบรรทัดอ่านแบบจดไว (หมวด/บัญชีเดาจากประวัติ ไม่ให้คะแนนช่วงเวลาของวัน) แต่ **ต้องพิมพ์ยอดเอง**; รายการโอนไม่รับ; วันที่ในอนาคต/วันที่ผิด = error; วัน+ประเภท+บัญชี+ยอดตรงกับที่มีอยู่ = ขึ้น "อาจซ้ำ" (ยังบันทึกได้)
- **บิลที่ถึงกำหนด**: บิลรอบนี้+รอบก่อนที่ `due_date ≤ วันนี้` ยังไม่จ่าย (ไม่รวม `auto:travel` และบิลหนี้ยอด 0) → กดจ่ายโดยวันที่ตั้งต้น = วันครบกำหนด
- **ค่าเดินทาง/หนี้**: วันทำงานที่ยังจดไม่ครบ (ย้อนหลังไม่เกิน 31 วัน) → เปิดหน้าวันทำงาน; บัญชี Ascend → หน้าเทียบยอด; SPayLater → ออเดอร์รอกดรับ
- **ปรับยอดให้ตรงยอดจริง** (`Store.adjustBalance`): เฉพาะบัญชีที่เปิดใช้และไม่มีตัวคำนวณหนี้; บัญชีเงิน ยอดจริงน้อยกว่า = รายจ่าย "ยอดที่ไม่ได้จด" (หมวด อื่นๆ), มากกว่า = รายรับ (รายรับอื่นๆ); วงเงิน ใช้ไปเพิ่ม = รายจ่าย, ลดลง = รายรับ (จ่ายคืน); ส่วนต่าง < 0.005 ไม่บันทึก; `source = adjust`

## 15. จุดอ่อนของระบบปัจจุบัน (ข้อเสนอแก้อยู่หัวข้อ 16)

1. **เขียนทั้งก้อนทุกครั้ง**: `Repository.edit` ล้างทุกตารางแล้ว insert ใหม่ทั้งหมด แล้ว `reload()`; แต่ละการเปลี่ยนแปลงตามด้วยการคำนวณใหม่ทั้งหมด (overview + debtStates พร้อมตารางผ่อน + outlook 6 รอบ) → ช้าเมื่อข้อมูลโต, เสี่ยงข้อมูลเสียถ้าโปรเซสตายผิดจังหวะ, ผูกกับอาการแอพเด้ง/กระพริบที่เห็นในประวัติคอมมิต
2. **config เป็นถังข้อมูลไม่มีโครงสร้าง**: ข้อมูลจริง (วันทำงานของรอบ, เหตุผลยกเว้น, % ภาษีต่อหมวด) ถูกยัดเป็นสตริง key/value; ลบหมวด/บัญชีแล้ว key ที่อ้าง id ค้างอยู่
3. **ใช้โน้ตข้อความเป็นตัวระบุ**: ขาไป/ขากลับค่ารถหาจาก `note == "ค่ารถไปทำงาน"/"ค่ารถกลับบ้าน"` — ผู้ใช้แก้โน้ต ระบบจะหาไม่เจอ
4. **magic string กระจาย**: `source`, `template_id` (`auto:debt`, `claim:`), `claim` (สถานะ+วันที่ในฟิลด์เดียว), `status` ของ Shopee มี `waiting` ที่ไม่อยู่ในคอมเมนต์ schema
5. **ข้อมูล derive เก็บซ้ำ**: ออเดอร์ food ↔ รายจ่าย, บิลหนี้อัตโนมัติ, `pay_cycle` ในรายการ (เปลี่ยนวันเริ่มรอบแล้วเพี้ยน), ยอด `est_amount` ของบิล SPayLater ต้อง sync ตลอด
6. **group + section ซ้อนกัน** และมีตรรกะเดา section ของแถวเก่า
7. **โอนข้ามสกุลเงินคิดยอดผิด** (ผู้เขียนอ่านจากโค้ด ยังไม่ได้ทดลอง): `Balances` บวก/ลบ `amount` เท่ากันทั้งสองบัญชี ไม่ดูสกุล
8. **Double กับ BigDecimal ปนกัน**: เก็บ BigDecimal แต่คำนวณ Double เพื่อให้ตรงระบบเดิม
9. **ผูกกับ JS reference**: ต้องดูแลสองฝั่ง, เทสต์ต้องมี Node, quirk ของ JS (`new Date(y, m, d)` ล้นเดือน, `jsNumber`, `jsPow`) ถูกจำลองในโค้ด Kotlin
10. **ฮาร์ดโค้ดชีวิตจริง**: ชื่อเล่นบัญชี (tm, kbank, ktb…), เดาบัญชีจากชื่อ ("true", "bangkok"), ค่ารถ 20/150, โครงการ 60/40 เฟส 2 (หมดอายุ 30 พ.ย. 2026), Ascend กับ SPayLater เป็นตัวเลือกเดียวของ `debt_engine`, broker ตั้งต้น "Dime!"
11. `copay_hours` ถูกเก็บแต่ไม่พบการตรวจเวลา; `summary_emails`/`reminder_emails` เป็นของเก่าที่ไม่ใช้
12. ไฟล์ UI ใหญ่ (TransactionSheet 639, Travel 588, PlanScreens 583 บรรทัด)
13. ไม่เข้ารหัส ไม่ซิงค์ ไม่มีสำรองอัตโนมัติ (มีแค่ Auto Backup + ส่งออกเอง)
14. ไม่มีค่าธรรมเนียมโอน; ไม่มีงบต่อหมวด (budget); ไม่มีรายการประจำที่สร้างรายการจริงอัตโนมัติ (มีแค่แผนบิล)

6. สำรองอัตโนมัติ + migration ของ schema
7. UI เป็นหน้าเล็กๆ มี state ของตัวเอง ลดกองหน้าซ้อน/overlay
8. ใช้ `pay_cycle` เป็นค่าคำนวณจากวันที่ + `pay_cycle_start_day` (หรือเก็บประวัติการเปลี่ยนวันเริ่มรอบ)

## 17. เกณฑ์ตรวจรับ (ตัวอย่างกรณีทดสอบที่ควรมี)

- รอบ: `payCycleOf("2026-10-14", 15) == "2026-09 Sep-Oct"`, `payCycleOf("2026-10-15", 15) == "2026-10 Oct-Nov"`; ช่วงของ `2026-10 Oct-Nov` = 2026-10-15 ถึง 2026-11-14
- Ascend: ค่างวด 10,000 / 5 งวด / 25% = `10000·(0.25/12)/(1−(1+0.25/12)^−5)` ปัด 2 ตำแหน่ง; ยอดเต็มจำนวนค้าง ≥ 300 ณ วันที่ 1 → แปลง 5 งวดอัตโนมัติ; ผิดนัดเงินต้นผ่อน ≥ 1000 → ค่าธรรมเนียม 50 แล้ว 100
- ตัดชำระ: ค่าธรรมเนียม → ก้อนที่ออกบิลแล้ว (ดอกก่อนต้น) → ยอดเต็มที่ยังไม่ออกบิล → ส่วนเกิน
- SPayLater: ออเดอร์วันที่ 14 ก.ค. งวด 1 ครบ 25 ก.ค.; ออเดอร์วันที่ 15 ก.ค. งวด 1 ครบ 25 ส.ค. (ตัดรอบ 15)
- 60/40: ราคา 500 รัฐจ่าย `min(300, เหลือวัน, เหลือเดือน, เหลือโครงการ)`; วันที่ 1 ของเดือนใหม่รีเซ็ตเพดานเดือน
- Staff Claim: ส่งเบิก 15 ก.ย. → ได้ 30 ก.ย.; ส่ง 16 ก.ย. → ได้ 30 ต.ค.; ส่ง 10 ก.พ. → ได้วันสุดท้ายของ ก.พ.
- แผนบิล: ลบรายการที่มาจากบิล → บิลกลับ planned; ลบบัญชีที่มีรายการ → error
- นำเข้า/ส่งออก: ส่งออกแล้วนำเข้าได้ข้อมูลเดิมเท่ากันทุกแถว (round trip)
- เทียบผลกับ `reference/run.mjs` ด้วย `sample-data.json` ทุกวันที่ในช่วง 100 วัน (ถ้าจะคงสเปกเดิม)

## 19. Golden tests — วิธีเอาของเดิมมาใช้

repo ใหม่ไม่มีไฟล์เหล่านี้ ต้องคัดลอกจากระบบเดิม (`coolza254-lgtm/DanshaISM`):

| ไฟล์เดิม | ใช้ทำอะไร |
|---|---|
| `reference/engine/*.js` | ตัวคำนวณเดิมที่รันได้ (สเปกที่รันได้ ผ่านการเทียบกับ Apps Script เดิมและ statement จริงแล้ว) |
| `reference/run.mjs`, `reference/verify.mjs` | รันอ่าน/แก้ข้อมูลตามสถานการณ์ และพิมพ์ตัวเลขหลักของวันนั้น |
| `reference/sample-data.json` | ข้อมูลสมมติ (ไม่ใช่ข้อมูลจริง) |
| `core/src/test/kotlin/.../ReferenceScenarios.kt`, `ReferenceTest.kt`, `JsHarness.kt` | ตัวอย่างวิธีเทียบ ~100 วัน (ทุก 2 วัน + วันออกบิล/ครบกำหนด) และขั้นตอนแก้ข้อมูล 100+ ขั้น |
| `core/src/test/kotlin/.../*Test.kt` | เทสต์หน่วยของ Forms, Home, PlanBook, QuickEntry, DataFile, Dates ฯลฯ |

วิธีที่แนะนำ: รันตัวเดิมด้วย Node สร้างไฟล์ผลลัพธ์ (JSON) ไว้เป็น fixture แล้วให้ตัวคำนวณใหม่เทียบกับ fixture — repo ใหม่จะไม่ต้องพึ่ง Node ตอนรันเทสต์ประจำวัน
ถ้าตั้งใจให้ผลต่างจากเดิม (เช่น แก้บั๊กโอนข้ามสกุล) ให้บันทึกเหตุผลและให้ผู้ใช้ยืนยันก่อน
หมายเหตุ: แอพเดิมใช้ `interestMode = 3` (ปัดดอกรายก้อนให้ตรงแอพ Ascend) ส่วนเทสต์เทียบ JS ตั้งเป็น 0 — golden test ของระบบใหม่ควรแยกสองชุดนี้ให้ชัด
